### Provider abstraction contract

Two provider paths wired end-to-end through `src/core/llm/providers.ts`:

**Groq path** — uses pi-ai's built-in Groq model registry.
- Env: `LLM_PROVIDER=groq`, `GROQ_API_KEY=<key>`
- Default fast model: `llama-3.1-8b-instant`
- Default reasoning model: `llama-3.3-70b-versatile`
- Override with `LLM_MODEL_FAST` / `LLM_MODEL_REASONING`

**Ollama path** — builds a custom `openai-completions` model against Ollama's OpenAI-compat endpoint.
- Env: `LLM_PROVIDER=ollama`, `OLLAMA_BASE_URL=http://localhost:11434/v1`, `OLLAMA_MODEL=qwen3.5:4b`
- Notable: pi-ai's openai-completions transport requires a non-empty `apiKey` argument even when the backend doesn't authenticate — the route passes the literal string `"ollama"` for the local path. This is safe because Ollama ignores it.

The `RoleName` type (`"fast" | "reasoning"`) is the abstraction the rest of the system will use when requesting models. Operations in later sprints ask for a role, not a provider.

### Known quirks discovered during Sprint 0

1. **pi-ai error events carry an `AssistantMessage` in `event.error`**, not a string. The real message lives at `event.error.errorMessage`. Our SSE dispatch now reads that field.
2. **User messages require `timestamp: number`** in pi-ai's `Context.messages` — not just `{role, content}`. Missed on first pass, caught by `tsc`.
3. **pi-ai's openai-completions transport rejects an empty API key** even for a custom baseUrl that doesn't authenticate. Workaround: pass `"ollama"` as a dummy for local models.
4. **`qwen3.5:4b`** is the model tag locally installed. `qwen3:4b` is also present — swap via `OLLAMA_MODEL` env var.

- **pi-ai is pre-1.0** (0.67.1 as of this writing). Breaking changes are likely. We depend on: `stream`, `Context` shape, `getModel('groq', …)`, `Model<'openai-completions'>` custom model shape, `AssistantMessageEventStream` event types. - **No test infrastructure yet.** `vitest` is installed but no tests have been written. Sprint 1 must land at least a couple of unit tests around parsing and the executor, otherwise coverage debt compounds fast.
- **Single-machine assumption.** Everything runs on localhost. No thought given to deploy, multi-user, or secret management beyond `.env.local`. Acceptable for the "local interface" phase of the project, but we should flag this if the product grows.
- **No structured logging yet.** `console.log` implicit. Operation Executor will need structured logging in Sprint 1 to make production issues debuggable.
- **pi-ai doesn't natively support Anthropic prompt caching via its unified interface in our code path** (we'd need provider-specific options). The implementation plan assumed cache_control would pass through — need to verify this survives the abstraction when we hit Sprint 6 batch ops.

### Key design decisions made during Sprint 1

1. **Storage signature: `update*` methods require `sessionId` in the updates payload.** The plan's interface shows `updateDocument(id, updates)` with no session hint, but documents are partitioned by session on disk. Rather than scanning every session directory to find a doc by id, I made `sessionId` mandatory in `updates`. This adds one field at every call site but eliminates an O(N) lookup per write. **Trade-off accepted.** Tested explicitly — `updateDocument({ content: "..." })` without `sessionId` throws a clear error.

2. **MemoryStorage clones aggressively.** Every read and every write JSON-round-trips the value. Slower than reference-passing but matches FileStorage's behavior exactly: a caller can never mutate stored state by holding onto a returned object. Sprint 1's "isolation" test set explicitly verifies this.

3. **File storage: one JSON file per collection per session, not one file per record.** Trade-off: rewriting the whole `messages.json` on every new message is O(N) in messages, but for sessions with <1000 messages this is negligible (sub-millisecond for typical sizes). Buys us trivial atomicity — one `rename` per write, no lock files, no per-record state to manage. The plan calls this out as a known limitation; SQLite is the migration path if it ever bites.

4. **`getStorage()` is a singleton, but tests bypass it.** The factory returns the same instance for repeat calls within a process, which is right for the app but wrong for tests. Tests construct `new FileStorage(...)` and `new MemoryStorage()` directly with their own temp dirs. `resetStorage()` exists as an escape hatch but tests don't currently need it.

5. **WireframeManager uses atomic writes too.** The plan's example used a non-atomic `writeFile`, but I used `tmp + rename` for consistency. Wireframe HTML files are small, the cost is negligible, and it prevents half-written files if the process crashes mid-generation.

6. **Vitest path aliases are mirrored manually**, not via `vite-tsconfig-paths`. One fewer dependency, one config file to maintain. Documented in `vitest.config.ts` that the list must stay in sync with `tsconfig.json`.

### What was NOT tested (Sprint 1 blind spots)

| Blind spot | Why not | Planned coverage |
|---|---|---|
| **Concurrent writes to the same collection** | Tests are single-threaded. Two simultaneous `addMessage` calls to the same session could race on the read-modify-write cycle, with the second clobbering the first. | Sprint 4 (Session Manager) — needs an in-process write lock per session. | **Crash mid-write** | We rely on `rename` atomicity, but never simulate a crash to verify a half-written `.tmp` doesn't pollute the active file. | Hard to test in unit tests; would need fault injection. Accept the OS guarantee for now. |
| **Filesystem permission errors** | We never run against a read-only directory or denied path. | Defer to integration tests — handled via thrown errors that bubble up to API routes. |

### Known quirks discovered during Sprint 1
